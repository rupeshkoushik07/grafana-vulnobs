# Deploy Vulnobs with Flux (GitOps)

An alternative to `tk apply` (see [`../tanka`](../tanka/README.md)): [Flux](https://fluxcd.io)
pulls the stack from this repository and keeps the cluster in sync with `main`.

Tanka stays the source of truth. Flux reconciles plain YAML, so the Tanka environment is
exported to [`apps/vulnobs/`](apps/vulnobs) and the result is committed:

```
deploy/flux/
├── apps/vulnobs/          # generated by tools/export-flux-manifests.sh, do not edit
│   ├── kustomization.yaml
│   └── <kind>-<name>.yaml
└── clusters/kind/
    └── vulnobs.yaml       # GitRepository (this repo, main) + Kustomization (apps/vulnobs)
```

## Changing the stack

Edit `deploy/tanka/`, then regenerate and commit the export:

```bash
tools/export-flux-manifests.sh     # needs tk on PATH
git add deploy/flux/apps/vulnobs
```

The [`flux.yml`](../../.github/workflows/flux.yml) workflow fails if the committed export is
stale.

## Bootstrap

1. Create the namespace and the storage Secret **out of band**. Secrets are never committed;
   the export script refuses to write one. Use the same steps as for Tanka
   ([Apply to a cluster](../tanka/README.md#apply-to-a-cluster)):

   ```bash
   kubectl create namespace vulnobs
   export VULNOBS_TOKEN_SIGNING_KEY="$(openssl rand -hex 32)"
   export VULNOBS_STORAGE_TOKEN="$(python3 tools/create-storage-token.py --tenant-id production-grafana)"
   kubectl -n vulnobs create secret generic vulnobs-storage \
     --from-literal=database-url='postgres://USER:PASSWORD@DB_HOST:5432/vulnobs?sslmode=require' \
     --from-literal=token-signing-key="$VULNOBS_TOKEN_SIGNING_KEY" \
     --from-literal=storage-token="$VULNOBS_STORAGE_TOKEN"
   ```

   To manage the Secret with GitOps as well, encrypt it with
   [SOPS](https://fluxcd.io/flux/guides/mozilla-sops/) or use an external secrets operator;
   don't commit it in plain text.

2. Bootstrap Flux against this repository (needs a `GITHUB_TOKEN` that can push to it):

   ```bash
   flux bootstrap github \
     --owner=rupeshkoushik07 \
     --repository=grafana-vulnobs \
     --path=deploy/flux/clusters/kind \
     --personal
   ```

   Bootstrap commits Flux's own manifests to `deploy/flux/clusters/kind/flux-system/`, and
   Flux then applies everything under `deploy/flux/clusters/kind/`, including
   `vulnobs.yaml`.

3. Watch it converge:

   ```bash
   flux get kustomizations --watch
   kubectl -n vulnobs port-forward svc/grafana 3000:3000
   ```

The Kustomization uses `prune: true`: deleting it, or a resource from the export, deletes
that resource from the cluster — including the `vulnobs` namespace, and with it the Secret.
The exported Deployments use `ghcr.io/rupeshkoushik07/grafana-vulnobs:main`; to pin a
release, set `spec.images` on the Kustomization or change `imageTag` in the Tanka
environment and re-export.

## Tested on every change

`flux.yml` builds the image from the commit under test, installs Flux in a throwaway
[kind](https://kind.sigs.k8s.io) cluster, points a `GitRepository` at that exact commit
(`refs/pull/<n>/head` for pull requests, so forks work too), overrides the image with the
CI build, and waits for the Kustomization to become Ready and Grafana to answer
`/api/health`. The full functional tests run in [`kubernetes.yml`](../../.github/workflows/kubernetes.yml).
